# 実装と評価の進行

ユーザーの要求から仕様を作り、実装・評価・改善を記録する。最終成果物は人が確認できるようにする。通常のコード変更には適用しない。

1. メインのエージェントがリポジトリの状態と既存の変更を確認し、固定するベースラインを特定する。`task-specification` の手順で仕様を作成し、必要な製品上の判断をユーザーに確認する。
2. メインのエージェントが確定仕様に基づいて実装する。適切な現在の作業領域を優先し、既存の変更と候補を安全に分けられない場合はベースラインから別worktreeを用意する。テスト名とテストの分担は [references/testing.md](references/testing.md) に従う。
3. 変更を候補差分として回収し、変更ファイル、テスト結果、未実施の項目を記録する。既存の作業を混ぜない。
4. 評価のみを別のサブエージェントに依頼する。評価者は別のクリーンなworktreeで候補を評価し、仕様、テスト、コード品質を確認する。詳細は [references/evaluation.md](references/evaluation.md) を参照する。評価サブエージェントを使えない場合は、その制約を報告し、別の評価者による確認を実施済みと扱わない。
5. 指摘があれば、そのIDを付けてメインのエージェントが修正し、評価サブエージェントが再評価する。メインのエージェントは差分、評価の根拠、テスト結果を確認する。ユーザーが指定した試行回数や停止条件を守り、未確認の評価を成功として扱わない。
6. 評価者とのレビューと必要な修正・再評価がひと段落したら、その時点の候補について、仕様と実際のテストケースの対応、評価結果、修正履歴を単一HTMLにまとめる。会話の最後にリンクを提示し、人間にレビューを依頼する。画面のある機能では、Playwright等で機能の操作動画と仕様・確認内容の注釈付き動画を撮影し、HTMLに埋め込む。このプロジェクトでは `viewer/README.md` と `viewer/FORMAT.md` を参照する。実際の実行結果を使い、未実施・未確認の項目はそのまま明記する。動画やHTMLを作れない場合は理由と代替の成果物を報告する。既存の動画や結果を、別の候補のものとして再利用しない。

試行と評価は同じホストで行う。別worktreeはファイルや評価資産へのアクセスを遮断しない。厳密な独立評価を行ったと主張しない。候補の適用失敗、評価環境の失敗、実装の不合格を区別し、根拠とログを保存する。`.harness/` は試行ごとの成果物に使い、秘密情報を保存しない。実装者が評価用資産にアクセスしないことを指示するが、同じホストでは技術的に保証できない。

報告では、実行内容、結果、変更箇所、成果物、未実施項目を示す。ユーザーが求めない限り、候補を元の作業領域に適用しない。
