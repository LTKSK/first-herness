# 実装と評価の進行

ユーザーの要求から仕様を作り、実装・評価・改善を記録する。最終成果物は人が確認できるようにする。通常のコード変更には適用しない。

1. メインのエージェントがリポジトリの状態と既存の変更を確認し、固定するベースラインを特定する。`task-specification` の手順で仕様を作成し、必要な製品上の判断をユーザーに確認する。仕様書の草案をユーザーに提示し、明示的な確認を受けてから確定する。仕様が確定するまで実装と評価を開始しない。ユーザーが実装を先に進めるよう明示した場合は、その指示に従う。
2. メインのエージェントが変更箇所と影響範囲を調べ、構造が実装やテストを妨げる場合は `refactoring` の手順で必要な範囲を整理する。メインのエージェントが確定仕様に基づいて実装する。適切な現在の作業領域を優先し、既存の変更と候補を安全に分けられない場合はベースラインから別worktreeを用意する。テスト名とテストの分担は [references/testing.md](references/testing.md) に従う。
3. 変更を候補差分として回収し、変更ファイル、テスト結果、未実施の項目を記録する。既存の作業を混ぜない。
4. 評価のみを別のサブエージェントに依頼する。評価者は別のクリーンなworktreeで候補を評価し、仕様書の確認項目、確認方法と根拠、テスト、コード品質を確認する。詳細は [references/evaluation.md](references/evaluation.md) を参照する。評価サブエージェントを使えない場合は、その制約を報告し、別の評価者による確認を実施済みと扱わない。
5. 指摘があれば、そのIDを付けてメインのエージェントが修正し、評価サブエージェントが再評価する。メインのエージェントは差分、評価の根拠、テスト結果を確認する。ユーザーが指定した試行回数や停止条件を守り、未確認の評価を成功として扱わない。
6. レビュー用の成果物を作る前に、実装と評価を踏まえて課題の仕様書を更新し、作業時の要求と判断を記録する。機能ごとの現在の仕様には候補の合意済みの振る舞いと確認項目、対応するテストを反映する。変更・廃止された記述は現在の仕様から取り除き、古い内容を注記として残さない。過去の内容は課題記録またはGit履歴で参照できるようにする。候補の現在の仕様を、マージ前の元のブランチの現状として扱わない。現在の仕様と課題記録をそれぞれ一覧から参照できるようにする。製品上の判断を変更する場合はユーザーに確認し、未確認の内容を確定事項として扱わない。各確認項目について実際のテストまたは他の確認方法と根拠、結果を記録し、未確認の範囲を明記する。確認項目に未実施・未確認・不合格が一つでもある場合や、評価の指摘が残る場合は完了としない。確認方法の追加、実行環境の調整、修正と再評価を行い、解消まで進める。確認不能の場合は、停止条件と権限の範囲内で解消に向けた対応を少なくとも一度試みる。停止条件に達した場合や対応しても確認できない場合は、未解決項目と試行の経緯を報告する。このプロジェクトでは `tasks/spec-test-map.md` を更新し、`node tasks/build-index.mjs` で `tasks/index.html` を生成する。評価者とのレビューと必要な修正・再評価がひと段落したら、その時点の候補について、仕様と実際のテストケースの対応、評価結果、修正履歴を単一HTMLにまとめる。会話の最後にリンクを提示し、人間にレビューを依頼する。画面のある機能追加では、Playwright等で仕様と確認内容の注釈付き動画を1本撮影し、HTMLに埋め込む。既存UIの改善・変更では、同じ操作について変更前と変更後の注釈付き動画を撮影し、新旧を同時に比較できる1本の動画に合成して、同じHTMLに埋め込む。新旧の対象と表示を明示する。動画では各操作の後に1秒の間隔を入れ、操作と結果が見えるようにする。このプロジェクトでは `viewer/README.md` と `viewer/FORMAT.md` を参照する。実際の実行結果を使い、未実施・未確認の項目はそのまま明記する。動画やHTMLを作れない場合は理由と代替の成果物を報告する。既存の動画や結果を、別の候補のものとして再利用しない。

候補をマージする前に、現在の仕様と確認項目・テストの対応が最終候補を反映していることを確認し、更新を候補に含める。振る舞いの変更がなければ現在の仕様を不要に変更しない。仕様の一覧HTMLと課題記録の一覧を更新し、差分を確認する。既存の一覧が課題記録だけを扱う場合は、現在の仕様と課題記録を区別して参照できるよう生成手順も整える。

試行と評価は同じホストで行う。別worktreeはファイルや評価資産へのアクセスを遮断しない。厳密な独立評価を行ったと主張しない。候補の適用失敗、評価環境の失敗、実装の不合格を区別し、根拠とログを保存する。`.harness/` は試行ごとの成果物に使い、秘密情報を保存しない。実装者が評価用資産にアクセスしないことを指示するが、同じホストでは技術的に保証できない。

報告では、実行内容、結果、変更箇所、成果物、未実施項目を示す。ユーザーが求めない限り、候補を元の作業領域に適用しない。
