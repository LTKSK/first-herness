# 実装と評価の進行

ユーザーが決めた課題と受け入れ条件を基に、実装・評価・改善を記録する。最終成果物は人が確認できるようにする。通常のコード変更には適用しない。

1. リポジトリの状態と既存の変更を確認する。課題、受け入れ条件、固定するベースラインを特定する。不足する情報は勝手に成功条件として扱わない。
2. ベースラインから実装用worktreeを用意する。利用環境で許可されていれば実装エージェントに課題と作業領域を渡す。実装者が使えるテストと記録方法も伝える。別エージェントを使えない場合は同じエージェントで作業したことを明記する。ベースラインにこのスキルが含まれるとは限らないため、必要な指示を明示的に渡す。
3. 実装者の変更を候補差分として回収し、変更ファイル、テスト結果、未実施の項目を記録する。既存の作業を混ぜない。
4. 別のクリーンなworktreeに候補差分を適用して評価する。課題の条件に合わせて仕様、テスト、コード品質を確認する。詳細は [references/evaluation.md](references/evaluation.md) を参照する。
5. 指摘があれば、そのIDを付けて修正と再評価を記録する。ユーザーが指定した試行回数や停止条件を守る。未確認の評価を成功として扱わない。
6. 求められた場合は、仕様とテストの対応、評価結果、修正履歴、機能の動画と注釈付き動画を単一HTMLにまとめる。このプロジェクトでは `viewer/README.md` と `viewer/FORMAT.md` を参照する。既存の動画や結果を、別の候補のものとして再利用しない。

試行と評価は同じホストで行う。別worktreeはファイルや評価資産へのアクセスを遮断しない。厳密な独立評価を行ったと主張しない。候補の適用失敗、評価環境の失敗、実装の不合格を区別し、根拠とログを保存する。`.harness/` は試行ごとの成果物に使い、秘密情報を保存しない。実装者が評価用資産にアクセスしないことを指示するが、同じホストでは技術的に保証できない。

報告では、実行内容、結果、変更箇所、成果物、未実施項目を示す。ユーザーが求めない限り、候補を元の作業領域に適用しない。
