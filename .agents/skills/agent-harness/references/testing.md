# テストの方針

## テストケース名

テストケース名は日本語で書く。失敗したときに、どの振る舞いが壊れたかを名前から判断できるようにする。

- 対象と必要な前提、操作または入力、期待する結果を示す。結果がどの対象に現れるかも明記する。
- 「状態を確認する」「表示が変わる」のように、対象や期待値が分からない表現を使わない。
- 「再起動」などの操作は対象を特定する。永続化の確認なら、同じDBを引き継ぐことと、どこで状態を確認するかを示す。
- 1つのテストケースは1つの守るべき振る舞いを表す。同じ振る舞いを確認するための複数のアサーションは許容する。条件が複数ある場合は、失敗した条件が分かるようにケース名を分ける。
- 仕様とテストケースを対応付ける。レポートには実際に実行したテストケース名とその結果を使う。対応するテストがない条件は未確認とする。

例: 「完了にしたタスクは、APIサーバーを同じDBファイルで起動し直した後も、タスク一覧APIで完了として返される」。

## テストの分担

- Integration testを中心に、APIやアプリの処理とデータ保存のつながりを確認する。テスト専用DBを使い、ケースを独立させる。外部環境が重くても、保存と読み出しの境界を確認するテストは残す。
- 複雑な判定や境界値、状態遷移、入力の組み合わせは、unit testで必要な条件を細かく確認する。実装の手順ではなく、期待される振る舞いを検証する。
- E2E testは、利用者の操作が実際の画面から成立することを確認する。下位のテストに置き換えられる組み合わせや境界値をE2Eで繰り返さない。

## mockの使用

実際の処理やテスト専用DBで安全かつ安定して確認できる場合は、それらを使う。テスト対象の処理や、その結果を確かめるために必要な保存境界を不必要にmockへ置き換えない。

外部サービス、時刻、実際には再現しにくい障害など、実物の使用が危険・不安定・過度に重い場合は、必要な境界だけを代替してよい。代替する理由と、実物につないだテストで確認していない範囲を記録する。障害のテストでは、確認したい失敗を再現できる方法を使う。

## E2E testを追加する判断

新しいE2E testは次の点を確認して決める。

1. 利用者が実際に行う操作や、利用者に見える結果か。
2. ブラウザーの操作、画面表示、画面からAPI・保存先までの接続など、実際につなげなければ見逃す問題があるか。
3. 既存のE2E testが同じ振る舞いを保証していないか。integration testやunit testに移しても必要な保証を失わないか。

実際につないだ確認が必要で、既存テストで保証されていない振る舞いにE2E testを使う。APIや処理だけで十分に保証できる条件はintegration testまたはunit testに置く。主要な利用手順や、下位のテストでは確認できない画面固有の失敗は残す。件数を一律に制限せず、追加・維持する理由と仕様との対応を説明できるようにする。
