# 評価

評価を始める前に、課題の条件と判定方法を固定する。テスト名とテストの分担は [testing.md](testing.md) に照らして確認する。仕様や評価方法を変更した場合は変更理由を記録する。評価者が定めたテストの実行結果だけでなく、何を検証したかと未確認の条件を残す。

- 仕様の評価: 要求と実装した振る舞いを照合する。曖昧な要求は一意の正解があると決めつけず、実装者の前提と確認の有無を記録する。
- テストの評価: 条件とテストを対応付ける。境界値、状態遷移、組み合わせ、ユーザー操作を必要に応じて確認する。意図的な欠陥を試すときは対象と変更点を保存し、元の候補と区別する。
- コード品質の評価: テストが守る振る舞いの分かりやすさや責務の配置を、合意済みの基準に照らして確認する。未合意のアーキテクチャを必須条件にしない。

## 現在の仕様と課題の記録

評価者は、変更された振る舞いと維持する振る舞いを課題の仕様と候補の現在の仕様で照合する。廃止・変更前の内容が現在の仕様に残っていないか、確認項目とテストの対応が最終候補に合うかを確認する。過去の判断や評価結果は、現在の仕様に混ぜず課題記録やGit履歴からたどれるようにする。

見た目の変更では、利用者が満たすべき条件を確認する。色、配置、余白などを仕様に固定する必要があるかは、合意された要件に照らして判断する。変更の意図と新旧の見た目はレビュー資料で示す。

## 確認項目と完了条件

受け入れ条件ごとに仕様書の確認項目を照合し、必要な振る舞いを確認できるか判断する。各項目にテスト、コマンド、画面操作、文書や設定の確認など適切な方法を選ぶ。テストを一律に必須とせず、継続的に守る必要のある振る舞いにはテストを優先する。評価者がその方法の妥当性と根拠を確認する。

各確認項目のID、方法、対象、根拠、実行結果、未確認の範囲を記録する。テストの場合は実際のテストケース名と実行結果を記録する。テスト以外の場合も、実施した操作や確認先と結果を具体的に残す。未実施や根拠不足は成功とせず、メインエージェントが補って評価者が再確認する。

すべての確認項目に妥当な方法、根拠、成功結果が揃い、評価の指摘が解消するまで完了としない。未確認や確認不能が生じたら、停止条件と権限の範囲内で原因を調べ、確認方法の変更や実行環境の調整など、解消に向けた具体的な対応を少なくとも一度試みる。試みた対応、結果、残る原因を記録する。指定された停止条件に達した場合や、対応しても確認不能で進めない場合は、未解決項目と試行の経緯を報告し、必要な判断をユーザーに求める。確認範囲を超える完全性を主張しない。

## 欠陥を入れたテストの評価

評価サブエージェントは、利用者にとって重要な振る舞いを選び、仕様に違反する変更を候補の別コピーに1件ずつ加える。元の候補と、そのテストは変更しない。元の候補でテストが成功することを先に確かめる。

このプロジェクトでは、関連する実装ファイルを選んで `npm run test:mutation -- <対象ファイル>` を実行し、StrykerJSを利用できる。画面の振る舞いを確認する場合は `npm run test:mutation -- --e2e <対象ファイル>` を使う。実行前に対象の仕様とテストを特定する。実行する範囲は課題に合わせて選び、選ばなかった範囲を明記する。実行方法と結果の保存先はREADMEを参照する。

Strykerのcommand runnerはテスト全体の終了コードで判定する。`Killed` でも構文エラー、起動失敗、DB障害や無関係なテストの失敗による場合は、対象の振る舞いを検出したことにしない。JSONの各変異の `statusReason` を確認し、対象のテストによる失敗かを調べる。`Survived` や `NoCoverage` は仕様に違反する変異かを確認し、等価な変異は見逃しと区別する。`Timeout` と `RuntimeError` は原因を確認し、テストの検出として数えない。この設定ではカバレッジ分析が無効なため、未実行の変異は `NoCoverage` として区別できない。スコアだけで合否や全体の網羅性を判断しない。

変更後は実装者の既存テストを実行し、期待した振る舞いの検証が失敗するかを確認する。評価用テストも実行する場合は、それぞれの結果を分けて記録する。ビルド失敗、起動失敗、タイムアウトなどで検証に到達しなかった場合は、テストが欠陥を検出したことにしない。

各試行について、対象の仕様、加えた変更、実行したテスト、期待した失敗、実際の結果、ログを記録する。結果は「対象の振る舞いのテストで検出」「検出されず」「判定不能」を区別する。変更が実際には仕様違反でない場合は、その理由を記録し、見逃しとして数えない。

検出されなかった欠陥は、テストの改善候補として指摘する。確認した欠陥の種類と未確認の範囲を示し、選んだ欠陥を検出しただけでテスト全体の網羅性を保証したと扱わない。

結果は `pass`, `fail`, `not_run`, `unknown`, `patch_error`, `environment_error` を区別する。テスト実行時の環境エラーの分類が不明な場合はログを残し、原因を調べる。評価が成功しても、網羅性や正しさが証明されたとは表現しない。

評価ID、対象の基準と差分、評価の種類、判定、根拠、指摘ID、実行時刻、ログの場所を記録する。修正は別の記録にして、対応した指摘IDと再評価IDを残す。動画は対象の候補と一致することを確認する。動画に映らない条件も、適切な別の確認方法と根拠があればその結果を表示する。いずれの方法でも確認できていない条件は未確認とする。

このプロジェクトの `.harness/evaluator/` に評価スクリプトがある場合は、その対象とベースラインを確認してから利用する。Git管理外なので他の環境では存在しない場合がある。期限追加用のテストを別の課題へ無条件に流用しない。
